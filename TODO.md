- [ ] **6. Search overlay.** `<leader>f` opens a floating pane with a one-line `TextBox` for the query and a read-only `TextBox` of results under it, built on 5b. Each result is a line, the first lines being the paths. Typing filters them, and `Enter` picks the line the results' cursor is on. The same shape later carries a file picker with a preview.
  - [ ] **Read-only `TextBox`.** A flag set by whoever owns the box. `edit` stays the one place the text changes, and a read-only box refuses it, so typing, `o`, `d` and `u` do nothing. Insert mode is a valid state of a read-only box, and so are select mode and every motion: only a change to the text is refused, and nothing else. What the owner puts in (`open_buffer`, `update`) is not refused, so it can fill the box. It is also what will lock a read-only file later, so a user can't make edits that are then lost. `check_invariants` states that a read-only box's text is only changed by its owner. The proof is a differential test: every action and key is run on a writable twin and on a read-only box. The read-only one never changes its text, and the actions it refuses are exactly the ones that changed the twin's text, so the check is exact and not just cautious. It is exhaustive over the finite list of actions and the default keys, which is cheap, and the random version stays in the fuzz test at its usual case count, which also sets the flag and compares the rope with a model that only the owner's calls change.
  - [ ] **A dry run of a key.** `TextBox::refuses(key)` says whether the key, in the box's mode and with its combo so far, would run an action that changes the text of a read-only box, without running it. It reads the key tree without advancing it (`Keymap::peek`), and `key_press` uses the same answer to do nothing, so what is refused and what is reported can't differ.
  - [ ] **Search overlay skeleton.** `open_search` on `<leader>f`, a centered pane with the query box (one line, starts in insert mode) above the read-only results, with static lines. Focus has no key of its own, and is read from the modes of the two boxes. The overlay passes a key to the focused box and then checks its mode. When the results box is in insert mode, the overlay sets it back to normal and the query box takes the focus, in insert mode. When the query box has left insert mode, the focus moves to the results. So `i` in the results and `Esc` in the query box are what move between them, and there is no focus flag to keep in step. Only the focused box sets the cursor. A key the results box refuses (`d`, `u`) does nothing. Both boxes use one target, `[keys.search.<mode>]`, over the shared keys: `Enter` is `pick_result` and `Esc` in normal mode is `close_overlay`, which is also the way out of the overlay. A `SearchAction` group in `OverlayAction`, and a `Scope` for it.
  - [ ] **The frontend finds the files.** The core never lists or matches files. Each time the query's text changes it sends `Output::Search { id, query }`, and the frontend answers with `Input::SearchResults { id, text }`, the lines to show, which the overlay gives to the results box as a new buffer, so its cursor and scroll are back on row 0. Typing a query and pressing `Enter` takes the top result. The `id` counts the searches, so a result that arrives for an older query is dropped, and a new query replaces the one before it. An `Enter` pressed before the answer to the latest query has arrived waits for it and then picks row 0, and doesn't pick a row of stale results. An empty query is sent too, so a backend can answer it with what was opened lately. The core's test double is a fake frontend that answers from a list, so everything about the overlay is tested with no disk. `pick_result` closes the overlay and runs `open` on the line under the cursor, which already shows an open document again and reads any other file, so item 7 only has to say what picking does to the document that was shown.
  - [ ] **Search channel to a command.** The frontend answers a query by running a command, and the user has to have it installed. It is one line in the config, `[search] command`, with a default that lists the files with `fd` and filters them with `fzf --filter`, and a user swaps either for `rg --files`, `sk`, a `zoxide` query and so on. It stays that simple on purpose: no matcher, no walker and no new dependency in wend, and what is left out is up to the command, which is why `fd` is the default lister, as it follows `.gitignore`. The rules the frontend keeps:
    - The query is never written into the command line, since a query is typed text: it goes in as the environment variable `WEND_QUERY` (`fzf --filter "$WEND_QUERY"`), and the command runs through `sh -c`.
    - One command runs per query on a worker thread, with its output read line by line up to a fixed number of lines, after which it is stopped. A new search stops the one before it, by killing the command's whole process group, so a `fd | fzf` pipe doesn't leave `fd` behind. The answer carries the `id` of the query it is for.
    - A command that can't start, or exits with an error that isn't "nothing matched", is sent back as `Input::Failed(Failure::Search { id, .. })` (item 5c), and the editor says so in the status bar (`search needs fzf: not found`) and leaves the results alone. A missing tool is a message and never a crash.
    - `fzf` reads its candidates from the pipe when it is not on a terminal, so the default has to be a pipeline and not `fzf` alone.
    - Spawning on each key costs a few milliseconds, and listing the files again each time may cost more on a big tree, so it gets a benchmark first (P-MEASURE) before anything is cached. If it matters, the frontend runs the lister once when the search opens and feeds the filter from that list, still with no matcher of its own.
    - `sh` makes this Unix only for now. A Windows frontend would need another shell, and that is left until there is one.
    - The built-in ripgrep libraries (`ignore`, `grep-regex`) stay an option for later, as a backend behind the same interface that needs nothing installed. That is when `rust-version` goes to 1.96.
  - [ ] **Preview side view.** A text box next to the results, holding the document of the line the cursor is on, which a user can edit fully and `Tab` moves into and out of. It is the one place a key does the focus, since the preview takes every key. Its edits are the document's own, so leaving or picking keeps them: the preview has to share the document with the editor, take it from `documents` or read the file through the event, and give it back. That is decided together with item 7.
  - Design notes: the search shares no code with the command line for now. If a third one-row prompt needs it, they become one custom element then. The default `<leader>f` is only a default, a config can bind another key to `open_search`. A result line is opaque to the core for now: it is what `open` gets, and a format such as `path:line` is read when something needs it.
