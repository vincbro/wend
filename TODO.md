The frontend runs it with `sh -c` the way the search does (its own process group, a line limit, stopped when it takes too long), and answers with `Input::ShellDone { id, status, text }`: the first lines of what it printed and how it ended. The editor shows that as a message and does nothing else, since a command may change the files on the disk (`touch`, `git checkout`), and a change to an open file already comes back as `Input::File`, which is the whole point of keeping the core from touching the disk.
  - [ ] **One flow or two.** The two are the same on the screen, a line in the status bar, and different in what they say: an error is a failure of something the editor asked, and a shell result is an answer, which can be good news. The proposal is one message flow with a kind (`Error`, `Info`), so one place draws, clears and keeps them (5c's `fail` becomes one way in of two), and two inputs, since what the frontend reports differs: `Input::Failed(Failure)` stays for failures, and the shell's answer is a result that a command's own failure (a status that isn't 0) turns into an error message. This is also where the severity that 5c left out comes in, with the rule in the theme (`Content::Error` next to a new `Content::Info`), and the history of messages (`:messages`), since a shell's output is longer than a row and has to be read after the next key. Decide this with the first one that needs it, and not before.
  - [ ] **What the output does.** A message is one row, so a longer output is cut in the bar and kept whole for `:messages`, or shown in a read-only overlay built on the read-only `TextBox` of item 6 when it has more than a line. Running a command and putting its output in a new unnamed buffer (`:sh!`-like) comes later and needs the unnamed buffer's name to be settled first.
  - [ ] **Safety.** The command is typed by the user and run as typed, as a shell does. Nothing the core reads from a file or a result is ever put in one, so a result line that looks like a command stays text.
- [ ] **6d. Overlays that keep their state.** Every overlay is dropped when it closes and built again when it opens (`CloseOverlay` sets the overlay to none, and `open_search` and the rest allocate a new one). That is simple and the allocation is not the problem, since it happens once per open. What is lost is the state: the last query of the search, where its results' cursor was, the command last typed, so opening the search again starts from nothing. The idea is to keep them, so an overlay is built once and hidden when it closes, and opening it shows what was there.
  - [ ] **Where they live.** The editor holds each kind of overlay it has opened (an `Option` for each, or a map by `OverlayKind`) and an index of which one is shown, so the one that takes the keys is still one. Opening takes it out of its slot or shows it, and closing only hides it. A config change has to reach the hidden ones as well as the shown one, which today only the open overlay needs, and the invariants have to check all of them.
  - [ ] **Clearing it.** What is kept has to be easy to throw away, and every box in an overlay is a full `TextBox`, so clearing one is the keys the user has already: select the row and delete it (`xd`). That doesn't work on the results of the search yet, because that box is read-only and refuses the delete, and its text is the frontend's to replace. So the clear is either a bind of its own (`clear_overlay`, or a `clear` action of each overlay's group that empties the query and asks for the empty search again) or the owner's call that already exists: opening the search with a fresh query is `open_buffer` on the box. Decide when the first overlay keeps its state. The query box has no such problem and is cleared with `xd`.
  - [ ] **What is kept and what is not.** The query and the mode of the search stay, and its results are asked for again when it opens, since the files may have changed while it was hidden (the id still counts up, so an answer that arrives late for the last session is dropped). The command line keeps its last text, and `Enter` still runs it and closes it. Whether a command line that is opened again starts empty is a choice: most editors do, so it may be the one overlay that clears when it opens.
- [x] **6e. Current line background.** The whole line the cursor is on gets its own background, set in the theme. A theme that doesn't want it gives the rule the same background as the plain one (or none), so there is no setting for it in the config and nothing to switch off in the core.
  - [x] **The layer.** `Style` gets a layer for it between the content and the selection, so the order is content, current line, selection, cursor, and a selected cell still shows the selection's background over it. The core marks every cell of the line the head is on, which is the whole logical line and so every row of a wrapped one, the blank cells to the end of each row included, so the color runs the full width and not only under the text. Every text box sets it, with no flag: the one-row boxes too, where it is the whole box, and the theme is what decides whether it shows.
  - [x] **The theme.** A `[current_line]` rule in `Theme` and in every theme file, with the comment that says what it colors and an example, identical in all of them as the theme tests require, and the rule count of the tests goes up by one. The default themes give it a background a little off the plain one. A user turns it off by giving it the plain background.
  - [x] **The cost.** `Style` is three bytes today, a `content` and two flags, and a test holds it there because every cell of every frame carries one. It is four now, and a cell 38 bytes instead of 37, since the flags were not packed into one byte. Packing them is left until the frame diff and the draw are measured (P-MEASURE). The diff also draws more cells: the cursor moving to another line redraws two whole lines, not a few cells.
  - [x] **Proof.** A test that every row of a wrapped line and the blank cells after its text carry it, that a line that isn't the cursor's doesn't, and that it keeps the selection's layer over it.
- [ ] **7. Multi-file waypoints.** Jump between open files. No splits or tabs.
- [ ] **8. Language registry.** File extension to language, replacing the hardcoded `"rust"`. Per-language settings (max width and tabs) read from `rustfmt.toml` by the frontend. Replaces layout's default width of 100.
- [ ] **9. Grammar pipeline.** Any tree-sitter wasm grammar from config paths, and building grammars from source. The build runs in the frontend and reports back as an event.
- [ ] **10. LSP.** A background process, JSON-RPC as events, diagnostics in the gutter, and a completion overlay. Last because it needs the layout, the registry and the background plumbing.
